Marker size is n for that bucket — several buckets are thin at n=120, so read the table below alongside the picture rather than the picture alone. The dashed grey line is the agent’s own belief (world_model_constants.P_RECOVERY_BY_BUCKET), shown for context and not as a target: that constant’s own comment calls it the probability of recovery on the NEXT SINGLE attempt, while “realized” here means recoverable at all, by retry or by link, within the simulation’s retry horizon — the same definition sim/generate_batch.py’s own summary line uses. Those are related but not identical quantities, so this plot is a check on ORDERING (does a higher bucket predict a higher chance), not on exact probability calibration.

What this says

The table orders cleanly; the model does not, and that is worth stating plainly rather than smoothing over. The table's realized rate is close to monotonic — VERY_LOW 0% up to VERY_HIGH 100%, with one dip at HIGH (60%, below MEDIUM's 70%). The model's is not: its OWN peak is MEDIUM at 87%, not VERY_HIGH, which realizes lower (70%) and sits close to LOW (67%). A reader relying on the model's recovery_bucket to rank “how good does this look” at the top end would be misled by it here.

This is a different axis from the 83%-vs-78% classification accuracy reported elsewhere in this repo (README) — that number is about getting the failure CLASS right; this one is about whether the recovery_bucket ESTIMATE, once a class is assigned, actually orders realized outcomes. Getting the first right does not guarantee the second, and this batch shows the model doing better on the first and worse on the second at the top of the range. Both are true, and un-averaged, on purpose.

Some of the ordering noise is explained by the gap the module docstring flags: the bucket is meant to rank a SINGLE-attempt hazard, but “realized” here is recovery within a 6-attempt horizon, and those compound differently per class — HIGH is dominated by SOFT_FUNDS; MEDIUM mixes SOFT_LIMIT (retryable) with SOFT_AUTH (link-only, at MEASURED_AUTH_HAZARD_1), and a class with a lower single-attempt hazard but more eligible attempts can out-realize one with a higher hazard and fewer effective tries. That explains the table's one dip. It does not obviously explain why the model's VERY_HIGH underperforms its own MEDIUM, since both classifiers are ranking the same underlying classes against the same horizon — the more likely explanation there is that the model spreads a wider, less selective set of cases into VERY_HIGH than the table does (n=47 against the table's n=18), diluting the bucket with cases the table would not have put there.

Where a bucket is thin (single digits, or VERY_LOW's table n=3), its point is not a reliable estimate of anything and the table above says so honestly rather than the chart implying otherwise by drawing a confident line through it anyway.
